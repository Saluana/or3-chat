# Requirements

## Introduction

This remediation closes the verified release-blocking defects from the OR3 Cloud sync/auth/storage audit and the chat orchestration/tool/persistence/streaming audit. The objective is not a cosmetic cleanup: authorization, convergence, storage integrity, side-effect safety, durable recovery, and protocol correctness must become explicit contracts that remain true across `or3-chat` and every maintained provider package.

`findings.md` is the combined evidence catalog. `tasks.md` is the single execution-status checklist; a finding is closed only when every linked task and regression test is complete.

## Context

The workspace is a Bun/Nuxt 4 monorepo-style collection rooted at `/Users/brendon/Documents/or3`, with the main application in `or3-chat` and separate Basic Auth, Clerk, Convex, SQLite, filesystem, and S3 provider packages. The current test suites are broadly green, but the audits demonstrated missing adversarial coverage around direct authorization, retained-log bootstrap, LWW convergence, workspace rebinding, destructive storage GC, tool replay, reload recovery, malformed SSE, and partial failure. Existing working-tree changes are user-owned and this plan assumes implementation will preserve unrelated modifications.

## Assumptions

- The release remains blocked until every Blocker and High finding in `findings.md` is closed and the release gates in R12 pass.
- Materialized workspace records, not retained change logs, are the canonical source for snapshots, quota, reference checks, and garbage collection.
- Sync history GC remains disabled until a snapshot-at-high-watermark bootstrap is implemented and verified.
- User identity and workspace scope are always derived from authenticated server context; caller-supplied identity fields are never authoritative.
- Side-effectful tools are untrusted execution requests even when generated by a selected model or provider.
- `tasks.md` owns checkbox state. `findings.md` uses open/closed status fields for traceability but does not duplicate task completion state.
- Provider interfaces may change when required for correctness, but compatibility adapters or explicit migrations are required for existing deployments.
- The work is implemented in small reviewable changes; no single pull request is expected to contain the entire program.

## Out of Scope

- New product features unrelated to the audited defects.
- Replacing Nuxt, Dexie, Convex, SQLite, S3, or the current provider registry solely for stylistic reasons.
- Rewriting the chat UI or sync engine when a smaller contract-preserving correction is sufficient.
- Migrating existing user content for reasons unrelated to new HLC, tombstone, snapshot, lease, reservation, or transcript requirements.
- Treating documentation-only changes as closure for a behavioral finding.

## Requirements

### R1: Authoritative authentication and authorization

**User Story:** As a workspace owner and operator, I want every cloud operation authorized from authenticated server context, so that callers cannot forge identity, role, workspace, or paid execution rights.

**Acceptance Criteria:**
- R1.AC1: WHEN a Convex identity, invite, membership, sync-write, or GC function is called THEN it SHALL derive the caller from authenticated identity and SHALL enforce the required capability before reading or mutating data.
- R1.AC2: IF the caller is unauthenticated, a viewer, or outside the target workspace THEN write, invite-management, identity-enumeration, paid-model, and destructive-GC operations SHALL fail without observable cross-tenant data.
- R1.AC3: WHEN a server tool executes THEN it SHALL receive authenticated user, workspace, thread, message, call, and abort context and SHALL pass an authorization decision before handler invocation.
- R1.AC4: WHEN a workspace is activated THEN authorization SHALL be evaluated against membership in the target workspace rather than only the currently active workspace.
- R1.AC5: WHEN invite-only registration is used THEN invite validation, identity creation, membership creation, and invite consumption SHALL be atomic and bound to the verified normalized email.
- R1.AC6: IF an identity provider supplies an unverified email THEN email-bound registration or invitation acceptance SHALL fail.
- R1.AC7: WHEN managed OpenRouter credentials are selected THEN the request SHALL be authenticated and SHALL possess the required paid/background capability; guest traffic SHALL use caller-supplied credentials.
- R1.AC8: WHEN authentication state changes or concurrent session requests resolve out of order THEN stale work SHALL NOT overwrite newer sign-out, identity, or workspace state.

### R2: Complete sync bootstrap and safe retention

**User Story:** As a user adding a fresh device, I want a complete consistent workspace snapshot before incremental replay, so that retention never makes older live records undiscoverable.

**Acceptance Criteria:**
- R2.AC1: WHEN a client with no trusted cursor bootstraps THEN the server SHALL return a consistent materialized snapshot plus a high-watermark and the client SHALL replay changes strictly after that watermark.
- R2.AC2: WHILE snapshot bootstrap is unavailable or unverified, change-log and tombstone GC SHALL remain disabled.
- R2.AC3: WHEN a device cursor is recorded THEN it SHALL be monotonic, integral, non-negative, and no greater than the server's current workspace version.
- R2.AC4: WHEN retention eligibility is calculated THEN timestamps, cursors, and retention bounds SHALL be server-derived or strictly validated and bounded.
- R2.AC5: WHEN snapshot or GC scans exceed one configured page THEN providers SHALL continue through bounded pages without unbounded in-memory reads.
- R2.AC6: IF a pull response includes `Retry-After` THEN the client SHALL honor the parsed delay within configured bounds.

### R3: Deterministic sync convergence

**User Story:** As a user editing from multiple devices, I want every provider and client to select the same winner, so that stale puts or deletes cannot resurrect, overwrite, or reorder data.

**Acceptance Criteria:**
- R3.AC1: WHEN resolving a put or delete THEN both materialized rows and tombstones SHALL be compared using the same `(clock, HLC, deterministic tie-breaker)` tuple.
- R3.AC2: WHEN multiple operations for one logical record occur in one page or batch THEN each operation SHALL resolve against the state produced by preceding operations in that page or batch.
- R3.AC3: WHEN an outbox operation is captured THEN the exact row revision tuple SHALL be written atomically to both the row and operation.
- R3.AC4: WHEN tombstones are created or migrated THEN they SHALL contain HLC and server-controlled deletion metadata sufficient for deterministic retention.
- R3.AC5: WHEN duplicate `op_id` values occur in one batch THEN identical operations SHALL be applied once and conflicting payloads SHALL be rejected before version allocation.
- R3.AC6: WHEN coalescing local operations THEN ordering SHALL use a monotonic revision sequence rather than millisecond wall-clock equality.
- R3.AC7: IF a payload attempts to change an existing row's logical primary key or indexed ownership fields THEN validation SHALL reject it.
- R3.AC8: WHEN generated provider templates are built THEN their LWW behavior SHALL be contract-tested against the application implementation.

### R4: Durable and private sync lifecycle

**User Story:** As a user working offline or across tabs, I want pending work and user-scoped data preserved correctly, so that retries, shutdown, and workspace changes do not lose or disclose data.

**Acceptance Criteria:**
- R4.AC1: WHEN an outbox operation exhausts automatic retries THEN it SHALL remain recoverable until an explicit retry or discard decision.
- R4.AC2: IF one operation in a pushed batch is malformed THEN valid siblings SHALL still receive deterministic results and the malformed operation SHALL receive an isolated permanent error.
- R4.AC3: WHEN a soft delete occurs THEN the sync layer SHALL emit a delete/tombstone operation rather than an ordinary put.
- R4.AC4: WHEN notifications synchronize THEN only their owning user SHALL be able to read or author them.
- R4.AC5: IF canonical content exceeds a transport limit THEN the operation SHALL fail visibly and remain recoverable, or use a lossless chunk/reference representation; it SHALL NOT replace content with a success marker.
- R4.AC6: WHEN sync is stopped THEN no in-flight callback, retry, or subscription SHALL recreate polling or subscriptions until an explicit start.
- R4.AC7: WHEN the active workspace changes THEN other tabs SHALL observe the revision and stale in-flight work SHALL NOT overwrite the new workspace state.

### R5: Canonical storage integrity, quota, and garbage collection

**User Story:** As a user storing attachments, I want CAS identity, quota, references, and garbage collection based on canonical state, so that live bytes are never deleted and invalid bytes never claim a trusted hash.

**Acceptance Criteria:**
- R5.AC1: WHEN quota or garbage collection evaluates a blob THEN it SHALL query canonical materialized metadata and references rather than reconstructing state from retained logs.
- R5.AC2: BEFORE deleting any blob or marker found through a partial listing THEN the provider SHALL verify its counterpart and canonical reference state with a complete listing or direct metadata lookup.
- R5.AC3: WHEN an upload is committed THEN a one-time upload intent SHALL bind workspace, object ID, expected SHA-256, maximum size, MIME policy, and expiry, and the provider SHALL verify actual stored bytes/metadata.
- R5.AC4: WHEN concurrent uploads reserve capacity THEN quota SHALL be atomically reserved before presign and consumed or released at commit/expiry.
- R5.AC5: WHEN metadata references disappear and retention expires THEN committed blob/marker pairs SHALL become eligible for bounded canonical GC.
- R5.AC6: WHEN `ref_count` is used THEN it SHALL be derived transactionally from canonical references or removed as an authority; sync SHALL NOT overwrite local derived values with meaningless provider defaults.
- R5.AC7: WHEN signed URLs are issued THEN their expiry SHALL not exceed the documented one-hour maximum.
- R5.AC8: WHEN GC scans large datasets THEN provider memory and per-run work SHALL remain within configured page and deletion limits.

### R6: Recoverable workspace-bound transfer execution

**User Story:** As a user uploading or downloading across reloads and workspace switches, I want every transfer bound to its originating workspace and recoverable, so that temporary absence never becomes replicated deletion.

**Acceptance Criteria:**
- R6.AC1: IF `storage_id` is absent or one remote lookup returns 404/410 THEN the transfer SHALL enter a typed pending/remote-missing state and SHALL NOT mutate synced deletion metadata.
- R6.AC2: WHEN a transfer is claimed THEN it SHALL capture immutable workspace/database context for its entire execution.
- R6.AC3: WHEN a process crashes or a lease expires THEN another worker SHALL atomically reclaim the transfer without two workers owning it concurrently.
- R6.AC4: WHEN a retry delay is scheduled THEN ordinary queue pumping SHALL NOT bypass the delay.
- R6.AC5: WHEN downloading content THEN bytes SHALL stream under a hard size limit, preserve verified MIME metadata, and avoid whole-payload double buffering.
- R6.AC6: WHEN a transfer settles, aborts, times out, or is disposed THEN all timers, waiters, object URLs, and listeners SHALL be released exactly once.

### R7: Safe tool definition and execution

**User Story:** As a user allowing AI tools, I want only explicitly offered and authorized calls to execute exactly once, so that model output cannot bypass permissions or repeat side effects.

**Acceptance Criteria:**
- R7.AC1: WHEN a chat request starts THEN it SHALL snapshot an immutable allowed-tool set; any returned name outside that set, disabled state, or runtime SHALL fail before handler invocation.
- R7.AC2: WHEN tool arguments arrive THEN a shared standards-compliant JSON Schema validator SHALL validate types, enums, bounds, nested requirements, and additional properties consistently on client and server.
- R7.AC3: WHEN a tool call ID is first observed THEN its name/argument fingerprint and result state SHALL be recorded; exact replay SHALL reuse the result and conflicting replay SHALL fail.
- R7.AC4: WHEN timeout or user/job abort occurs THEN cooperative handlers SHALL observe an aborted signal, timers SHALL be cleared, and no later loop iteration SHALL start.
- R7.AC5: WHEN a handler returns data THEN input, persisted output, UI preview, model-facing output, SSE state, and logs SHALL obey explicit UTF-8 byte limits.
- R7.AC6: WHEN plugins register or replace tools THEN ownership-bound disposers SHALL prevent one plugin from unregistering another plugin's active handler and watchers SHALL be released.

### R8: Deterministic chat request orchestration

**User Story:** As a chat user, I want send, retry, continuation, navigation, and composer behavior to have explicit state transitions, so that races and rejected operations do not corrupt or erase conversation state.

**Acceptance Criteria:**
- R8.AC1: WHEN send begins THEN request admission SHALL be atomic before the first asynchronous operation and all mutable request state SHALL be request-scoped.
- R8.AC2: WHEN a tool loop produces multiple assistant turns THEN cumulative UI content and per-iteration provider content SHALL remain distinct and the iteration cap SHALL terminate with an explicit error.
- R8.AC3: WHEN retry is requested THEN the original branch SHALL remain intact until the replacement is durably accepted; retrying an older turn SHALL exclude later future/tool rows from the replacement context.
- R8.AC4: WHEN a send is rejected before durable acceptance THEN composer text and attachments SHALL remain available.
- R8.AC5: WHEN parent or synced history changes THEN UI history and model history SHALL update atomically from one canonical source.
- R8.AC6: WHEN chat instances are replaced or disposed THEN hooks, watchers, background subscriptions, registry handles, and prompt-selection instances SHALL be released exactly once.
- R8.AC7: WHEN trimming model input THEN the returned transcript SHALL be within the configured token budget except when the protected system plus final-user messages alone exceed it, and tool-call/result groups SHALL remain valid.

### R9: Canonical and recoverable chat persistence

**User Story:** As a chat user, I want reloads and concurrent updates to preserve the exact transcript and generation status, so that recovered model context matches the visible conversation.

**Acceptance Criteria:**
- R9.AC1: WHEN tool calls and results are persisted THEN one canonical transcript representation SHALL reconstruct valid provider order and IDs after reload in both foreground and background modes.
- R9.AC2: WHEN streaming updates a message THEN it SHALL transactionally patch only stream-owned fields against the latest row and SHALL retain concurrent metadata, edits, files, and tool state.
- R9.AC3: IF background start fails before a durable job ID exists THEN the placeholder SHALL become a terminal error or be deleted; it SHALL NOT remain pending after reload.
- R9.AC4: WHEN a background tracker is created THEN it SHALL retain its originating workspace/database identity and SHALL NOT abort because another workspace becomes active.
- R9.AC5: WHEN a foreground stream is detached, revisited, or found pending after reload THEN it SHALL reattach through a persisted lease or become an explicit interrupted terminal state.
- R9.AC6: WHEN continuation starts THEN the persisted target SHALL receive the new stream identity, cleared prior error, and `pending:true` before the first delta.
- R9.AC7: WHEN tool or workflow metadata changes without content growth THEN the change SHALL still become durably visible within the configured persistence interval.
- R9.AC8: WHEN messages share or approach adjacent order indices THEN insertion and reads SHALL use the deterministic `(index, order_key)` ordering contract.

### R10: Correct streaming protocol, retry, abort, and recovery

**User Story:** As a chat user, I want transport failures and aborts represented accurately, so that a temporary network problem is not reported as model failure and a terminal signal always terminates work.

**Acceptance Criteria:**
- R10.AC1: WHEN parsing SSE THEN optional whitespace, multiline data, split UTF-8, final unterminated frames, provider error envelopes, and exactly one terminal event SHALL be handled correctly.
- R10.AC2: IF polling fails transiently THEN the client SHALL retain the active tracker and retry with bounded jitter; only authoritative server terminal state or bounded not-found reconciliation may terminalize the job.
- R10.AC3: WHEN abort occurs before headers, during body consumption, during retry delay, or during a tool handler THEN final state SHALL remain aborted and SHALL NOT be overwritten as error or completion.
- R10.AC4: WHEN upstream headers or body events exceed configured response/idle deadlines THEN composed abort signals SHALL terminate blocked I/O and persist a typed terminal state.
- R10.AC5: WHEN foreground and background consume the same normalized stream events THEN they SHALL satisfy one shared parity contract for text, reasoning, tools, limits, terminal state, and persistence flushes.
- R10.AC6: WHEN an accumulator finalizes as aborted THEN its public state SHALL expose that distinction and reset SHALL clear it.

### R11: Bounded performance and privacy

**User Story:** As an operator and user, I want streaming resource use and diagnostics bounded without leaking content, so that slow clients, reasoning-heavy models, and large tool outputs cannot exhaust resources or expose secrets.

**Acceptance Criteria:**
- R11.AC1: WHEN live job events are available THEN viewers SHALL NOT independently hot-poll the provider; reconciliation polling SHALL be shared and adaptive.
- R11.AC2: WHEN a viewer is slow THEN queued SSE bytes SHALL remain under a configured cap, cleanup SHALL run on cancellation and close, and the viewer SHALL resume from an offset after reconnect.
- R11.AC3: WHEN streaming text, reasoning, tools, or workflow state THEN durable writes SHALL be coalesced by time/size with an unconditional terminal flush.
- R11.AC4: WHEN production diagnostics are emitted THEN prompts, bearer/cookie credentials, tool arguments/results, emails, passwords, and arbitrary content SHALL NOT appear in logs or cache keys.
- R11.AC5: WHEN legacy diagnostic message capture is enabled THEN it SHALL be development-only, redacted, bounded, and disposable; otherwise the unbounded global archive SHALL be removed.

### R12: Provider parity and release verification

**User Story:** As a maintainer, I want every provider and generated template held to the same contracts, so that fixes in the application cannot regress in packaged deployments.

**Acceptance Criteria:**
- R12.AC1: WHEN direct, gateway, generated-template, static, SSR, and background variants are built THEN contract tests SHALL verify identical authorization, convergence, storage, tool, and streaming invariants where applicable.
- R12.AC2: WHEN static generation runs with cloud/auth disabled THEN cloud and auth provider runtime modules SHALL not load.
- R12.AC3: WHEN schema changes add HLCs, leases, reservations, snapshots, or transcript fields THEN migrations/backfills SHALL be idempotent and SHALL include rollback or forward-repair procedures.
- R12.AC4: BEFORE release THEN all Blocker and High findings SHALL have completed linked tasks, regression tests, type checks, import-boundary checks, provider tests, and required builds.
- R12.AC5: BEFORE a finding is marked closed THEN its regression test SHALL fail against the pre-fix behavior and pass against the fix, or the task SHALL record why a deterministic pre-fix test is impossible.
